1.Harness-level limits for coding agents with real access

  • Adversarial robustness
  • Agents
Setting
AI coding agents working in a production codebase, with reach into shared databases, a staging server, version control, the ticket system, and customers' accounting and tax integrations. This is tooling I set up for my own day-to-day engineering work at my employer. It is not a product.
Threat model
The agent takes a harmful action while following a plausible instruction, whether from me, from a stale note, or from text it read in a file, log or ticket. The actions that matter are irreversible or outward-facing: pushing code, deploying, committing credentials, editing tickets, sending data to a customer's live external account.
Controls
Two layers, kept separate on purpose.
  • Enforced by the harness: a pre-action hook that blocks a push when the branch conflicts with mainline, and a pre-commit guard that refuses credential and local-only files in every worktree.
  • Enforced by standing rules: each irreversible action needs a fresh human request; approval never carries over to the next task. Before any test on a copy of customer data, every outbound integration on that copy is switched off and verified.
What I learned
Rules in the prompt fail silently; hooks fail loudly. Every rule I later moved into a hook was one that had been broken at least once. The cost side matters too: a control that interrupts normal work gets bypassed, so each one was tuned to fire only on the dangerous action.
Limits
No measured attack set. This is defence built from incidents, not from red-teaming.
Result
In daily use since July 2026. The push guard merged mainline automatically on 201 pushes and blocked 166. None of the 166 was a real conflict; all were uncommitted local files, which showed me how often a blunt control fires on harmless work. The commit guard refused 3 commits that carried local-only patches.

2.Safety limits on a customer-facing AI assistant

  • Behavioral monitoring
  • AI control
Setting
An in-app assistant answers staff questions by looking up live business data in a multi-tenant ERP. I built the server-side controls; the settings screens were built by a colleague.
Threat model
A user asks the assistant for data they should not see, sends a question it should not act on, or uses it heavily enough to slow the shared system for every customer.
Controls
  • Input screening: every message in the conversation is screened before the model sees it, after hidden and look-alike characters are removed. The screen refuses attempts to override the assistant's instructions and requests involving payment card or bank account numbers. After a set number of refusals the user is paused, staff are alerted, and only an administrator can lift the pause.
  • Output filtering: protected fields are stripped from what the assistant can return, whatever the question.
  • Resource limits: a busy limit per customer and a time limit on every lookup, so one user cannot exhaust the system.
  • Feedback loop: users rate answers. Answers are kept 48 hours for rating and feedback text is cleared after 90 days.
What I learned
Each control needs a decision about which way it fails. Here, if the rate limiter or the pause check is unavailable, the question still goes through and the failure is logged. That favours availability and was a deliberate choice for this product; for a higher-stakes assistant I would choose the opposite. A review before release also found that the screen judged only the latest message, so a refused request planted in an earlier turn reached the model unscreened. Every turn is now screened.
Limits
The controls fail open. The load test ran on a laptop with a stand-in model, and the how-to evaluation is not yet valid, so I cannot state how often the screen is right.
Result
Merged November 2026. In a load test with a stand-in model, 60 simultaneous users for 90 seconds produced 776 busy refusals, 24 answers and no server errors, and no customer ever had more than 3 questions running. Number answers passed 8 of 8 evaluation cases; the how-to evaluation is not yet valid.

3.A verification layer over AI reviewers

  • Behavioral monitoring
Setting
AI agents review code changes that touch money and stock. This is tooling I set up for my own day-to-day engineering work at my employer. It is not a product.
Problem
A single reviewer is confident and often wrong. A false finding costs more than a missed one, because someone acts on it.
Design
  • Independent reviewer agents, each given one lens (removed behaviour, cross-file effects, language pitfalls, efficiency, and others) over the whole change, so their errors are less correlated than reviewers split by file.
  • A separate verification pass checks every finding against the actual code before it reaches a person. Unverified findings are dropped, not softened.
  • The monitor is tested too: I break the code on purpose and confirm the tests fail, and a contract test asserts each test fake still matches the real class.
What I learned
The verifier is only useful if it sees the code and not the reviewer's reasoning; given the conclusion, it tends to confirm it.
Limits
No labelled set, so I cannot state precision or recall. Building one is the obvious next step.
Result
In use since late September 2026 on 78 tickets. At least 41 reviewer claims were dropped after checking them against the code or data, and at least 129 issues were fixed before merge. In one case a review found a way past an administrator check; it was reproduced and fixed before release.

4.Deterministic checks on an LLM that proposes financial records

  • Behavioral monitoring
  • AI control
Setting
An LLM reads supplier invoices and matches them to purchase orders in a multi-tenant ERP. Accepted output becomes bills and cost entries in customers' books.
Threat model
The model's output is untrusted: a misread quantity, an invented line, a match to the wrong order.
Control
The model proposes; server-side rules decide. A billed quantity cannot exceed what was ordered or received. Cost increases beyond a set rule are refused. Charges the model cannot match go to a fixed, typed category instead of a guess. Large jobs run in a queue, and every refusal carries a reason code that reaches a person. Posting without a person is off by default. Only an administrator can switch it on, normally the customer's own, and must name an accountable user who is active and allowed to post bills; the server re-checks that on every save. Automatic posts run under that user's name and can be limited to chosen suppliers. A bill posts on its own only when it matches the order closely enough. Anything else goes to a review list, the responsible person is notified, and it stays there until a person handles it.
What I learned
  • Cheap deterministic checks catch a large share of harmful output when the domain has hard invariants.
  • They do not catch a wrong assumption in the prompt. One rule in the reader's prompt said a size is a garment size. Nobody had asked for that rule; an AI coding agent had written it in, and it was copied to a second reader. Every non-garment line was flagged as a wrong size until a tester noticed about three weeks later. The fix was small. The lasting change was a rule for the agents: no business rule goes into a prompt unless a person stated it.
  • The open question, and the one I would like to study, is what to do where no invariant exists and the monitor must itself be a model.
Result
First version merged October 2026. Review before release found and fixed 26 issues across the two readers, and 678 unit tests now cover reading and matching. Production volumes are not included here.

5.Removing client-side authority over AI metering and spend

  • Adversarial robustness
  • Attack surface
Setting
Prepaid, per-customer metered AI usage, billed through a separate billing system.
Attack surface
The client application could influence values that billing and limits depended on: prices, settings and usage records.
What I did
  • Audited every write path. Usage is recorded only by the server at the point of the model call; prices and settings change only through a platform administrator.
  • Set each customer's spend cap at the model provider from that customer's paid credit, so a defect in our own metering cannot overspend.
  • Signed the messages between the product and the billing system; an unsigned message is refused.
  • AI document reading is off by default behind a platform-set master switch.
Result
Closed 4 client-callable usage-write calls, 6 settings routes (2 of which had needed no sign-in) and 1 pass-through route to the model provider. The API key no longer leaves the server. 11 administrator actions sit behind a tested gate, backed by 238 unit tests. Running in the test environment and connected to the billing system; not yet released to production.
